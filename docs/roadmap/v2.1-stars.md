# KAOS v2.1 roadmap — from 9 stars to thousands, without spamming

*Written 2026-09-02, one day after the 2.0.x launch. Produced by running KAOS 2.0.2 on
the question (four parallel agents, `agent_sdk` provider) plus verified external evidence;
method and audit trail in §6. Continues `v0.11-adoption.md`, whose P0+P1 shipped as 2.0.x.*

## 0. The answer in three sentences

The projects in KAOS's category that went from zero to tens of thousands of stars in 2026
did it with **one command that installs into the tool developers already run every day**
(Claude Code), **one hard number on a benchmark outsiders recognize**, and a story that a
stranger can retell in a sentence. KAOS has the substance for all three — a flight recorder
+ shared memory that runs local with no embeddings, and a discipline nobody else has — but
none of them is *packaged* yet: there is no Claude Code plugin, no external benchmark score,
and no benchmark of our own that others could run. The plan below ships those three, in
that order, in ~60 maintainer-hours, each behind a leading indicator that is measurable in
30 days and is not a star count.

## 2. The six moves, ranked by leverage per maintainer-hour

Gates are binding where we control the outcome (a file exists, a test passes, a latency
budget holds) and directional where the world decides (downloads, external runs).

### M1 — Claude Code plugin: `claude plugin marketplace add canivel/kaos` (10–12 h) — HIGHEST

The wedge. A plugin directory in this repo (`plugins/claude-code/`) with:

```
.claude-plugin/plugin.json     name "kaos", version, description, homepage, license
.claude-plugin/marketplace.json  so `claude plugin marketplace add canivel/kaos` resolves
hooks/hooks.json               real format: {"hooks": {"SessionStart": [{"hooks": [{"type":"command","command":"…"}]}], …}}
.mcp.json                      the existing 58-tool server, auto-registered — no manual JSON editing
skills/kaos-recall/SKILL.md    /kaos:recall <query> — memory search from inside a session
```

Hook mapping onto **existing** mechanisms (no new mechanism, one new CLI verb):

| Hook | Calls | Budget |
|---|---|---|
| `SessionStart` | `kaos memory search "<basename cwd>" --rank weighted -n 5 --format inject` → stdout becomes context | ≤ 400 ms |
| `UserPromptSubmit` | `kaos memory search "<first 120 chars of prompt>" -n 3 --format inject` | ≤ 200 ms |
| `PostToolUse` (async) | `kaos journal append --agent claude-code --session $id --event tool_use --stdin` | ≤ 80 ms |
| `Stop` (async) | `kaos journal append … --event session_stop`, then `kaos dream consolidate --apply` | ≤ 500 ms |

Needed in core (all thin): `kaos journal append` (there is **no** CLI today to write an
external session's events into the journal — the runner writes them internally),
`--format inject` + `--token-cap` on `kaos memory search`, and `kaos connect claude-code`
as the no-marketplace fallback that writes the same files into `.claude/`.

**Measured risk — this reshapes M1.** `kaos memory search` cold start measured **710–830 ms**
(5 runs, this WSL machine, db on a `/mnt/p` mount; expect roughly 150–300 ms on a native
disk — still over the 200 ms prompt-time budget). The cost is `click` + `rich` + `yaml`
imports, not the 9 ms query. So: (a) hooks call a dedicated lightweight entrypoint
(`kaos-hook`, imports `sqlite3` + `kaos.memory` only — target < 60 ms) rather than the full
CLI; (b) the `UserPromptSubmit` hook ships **off by default** until the pre-registered latency
probe ACCEPTs it; SessionStart + async journaling alone already deliver the claude-mem
experience. A socket-mode daemon is the follow-up, not a prerequisite.

**Gates.** G4.1a (binding): on a clean machine, `claude plugin marketplace add canivel/kaos
&& claude plugin install kaos@kaos` followed by one session leaves rows in `kaos.db` and the
next session shows an injected memory block; test in CI with a synthetic hook payload.
G4.1b (binding, pre-registered probe): hook p95 ≤ 400 ms SessionStart, ≤ 200 ms
UserPromptSubmit over 50 cold runs at a 10k-agent db; REJECT → drop the prompt hook, logged.
G4.1c (directional, +30 d): plugin submitted to `claude-plugins-community`; ≥ 1 issue or PR
from a non-author about the hooks.

### M2 — Own the memory numbers: PRG + pre-registered LongMemEval split (14–16 h)

Two benchmarks, both runnable from a clean checkout in < 10 minutes, both hash-locked
before the first run, results committed whatever they are.

- **PRG — Paraphrase Recall Gap** (`benchmarks/prg/`, 4–6 h). 50 (stored-phrase,
  paraphrased-query) pairs drawn from real incident vocabulary (issue #42's "double charge"
  vs "duplicate processing" is pair #1). Publishes KAOS's miss rate honestly — expected
  80–90% — and becomes the acceptance gate for *any* future paraphrase fix (query-time
  expansion via the LLM already in the loop, trigram tokenizer, alias column — no embeddings).
- **LongMemEval, split-reported** (`benchmarks/longmemeval/`, 8–12 h). Dataset is MIT, on
  Hugging Face, 500 questions, session-level `answer_session_ids` for recall@5 — an FTS
  memory can run it honestly by indexing each haystack session as a memory entry. Pre-register
  a mechanical split (question shares ≥ 1 content 3-gram with the gold session → *verbatim*,
  else *paraphrase*) and gates: **ACCEPT** verbatim R@5 ≥ 0.70 at p95 < 25 ms; **REJECT** < 0.60;
  **VOID** split yields < 50 verbatim questions. Publish both buckets and the split labels.
  **Never publish the aggregate alone** — expected 50–65% vs MemPalace's 96.6%, and the
  aggregate without the split is a liability; with the split and the lock it is the credibility
  story ("we ran their benchmark, pre-registered, and published the number we got").

**Gates.** G4.2a (binding): both `preregistration.json` files committed with sha256 before
any run; `kaos experiment log` rows for both runs. G4.2b (binding): README carries the
split-reported table with a reproduction command. G4.2c (directional): issue #42 updated with
the PRG link; ≥ 1 external proposal referencing PRG as its acceptance criterion.

### M3 — Agent Forensics Bench (AFB) + `kaos-eval` Action (18–22 h)

The aider play on our own court. AFB v1 measures what no benchmark measures and what
production/compliance buyers ask: checkpoint fidelity (restore hash == checkpoint hash),
journal completeness (% of tool calls present in the append-only journal), cross-agent
isolation (0 leaks), fault localization (entries an auditor inspects before finding the
decisive step; median ≤ 5), mid-task recovery overhead (< 20%). Binary tests are
structurally verifiable by anyone; `compat/run_external.md` explains how to run it against
Pi, claude-mem, LangGraph. KAOS pre-registers its own self-test (ACCEPT = all binary tests
100%) — if it fails, that is a bug found, published.

`kaos-eval` becomes a reusable GitHub Action on the Marketplace: runs PRG, LongMemEval
split, AFB on every release, fails on REJECT/VOID, uploads results. It dogfoods the
discipline and gives other projects a one-line way to run AFB in their CI.

**Gates.** G4.3a (binding): AFB spec + generator + runner committed; KAOS self-run result
in `benchmarks/afb/results/`. G4.3b (binding): Action green on a KAOS release; listed on
the Marketplace. G4.3c (directional, +60 d): one external run, issue, or citation.

### M4 — Terminal aha with measured numbers (4–6 h)

`kaos demo` already exists and needs no keys, but it seeds a db and opens a browser UI.
Add `kaos demo --print` (or `kaos aha`): in-memory SQLite, deterministic seed, 10k agents ×
50 memories, one real FTS query with the **measured** elapsed time (never a hard-coded
"9 ms"), a 3-row audit-trail table, and the plugin one-liner — ≤ 30 lines, < 10 s, exit 0,
no network. Its output becomes the first screen of the README.

**Gate.** G4.4 (binding): `uvx --from kaos-harness kaos demo --print` passes a CI test on a
clean runner in < 10 s with no env vars; README's first 40 lines contain the output.

### M5 — `pi-kaos` extension (5–7 h, after M1 shows traction)

Same hook mapping, Pi's API: `pi.on('session_start' | 'tool_result' | 'turn_end')`,
`pi.registerCommand('kaos-recall')`, ~60 lines of TypeScript shelling to the `kaos` CLI.
Separate repo `canivel/pi-kaos` (Pi's ecosystem is npm/git packages; this is the one
exception to "one package" and it is not a Python package). One integration done well
beats two done at once — start only after G4.1a passes.

**Gate.** G4.5 (directional): published; ≥ 50 installs/month at +60 d.

### M6 — Contribution surface (4–5 h)

`contrib/plugin-template/` (pyproject with the `kaos.plugins` entry point, a provider stub,
an MCP tool-pack stub, a test), `CONTRIBUTING.md` that explains the kill-gate discipline
applies to *core mechanisms*, not to community plugins, and five `good first issue` items
that are plugin-shaped. **Gate.** G4.6 (directional): first merged PR from a non-author.

## 4. What not to do

- **No posts, threads, or launches before M1 + M4 exist.** Traffic without a 60-second
  install converts to nothing; four independent agents and every comparable's history agree.
- **No embeddings to chase MemPalace.** "Local, no GPU, no embeddings" is the story, and any
  paraphrase fix must pass PRG under a pre-registered gate first.
- **No aggregate LongMemEval number** without the split and the lock.
- **No ARC-AGI-3 narrative for growth.** Remarkable result, wrong audience.
- **No herdr/tmux `fleet attach` before M1.** Right feature, smaller audience, needs infra a
  newcomer doesn't have.
- **No new paper before a benchmark number exists.** The paper writes itself afterward.
- Standing rules hold: one package + plugins, no litellm, no openai SDK, KAOS is the layer
  under coding agents, not one of them.

## 5. Verdict framing

This is a probe. If M1 + M2 + M4 ship with their binding gates green and, 60 days later,
G4.1c / G4.2c / G4.3c are all still empty (no external issue, run, or PR), the hypothesis
"attach to Claude Code + publish honest numbers" is **REJECTED** for a one-maintainer
project, and the next candidate (kaos-eval/AFB as the standalone flagship) gets its own
pre-registration. Log it in the experiments journal, `family=adoption`, like everything else.

## 6. How this was produced (and what it caught)

- Evidence gathered from primary sources (pi.dev docs, MemPalace README, LongMemEval repo,
  Claude Code plugin docs, GitHub/PyPI APIs) and written into a brief with the constraint
  "do not invent numbers beyond these".
- KAOS 2.0.2 ran four agents in parallel (`kaos parallel`, `agent_sdk` provider,
  claude-sonnet-4-6) with lenses *growth*, *dx*, *integration*, *credibility*. Each wrote
  `/report.md` in its own sandbox; reports were pulled with `kaos read`. All four completed
  (ok); the run's `kaos.db` (729 KB) holds the full audit: 4 spawns, 5 tool calls, 34 events.
- **Consensus without coordination:** all four ranked the Claude Code plugin first or second;
  three called for a pre-registered benchmark and for publishing a REJECT if that is the
  result; all four independently said "no posts before the install works".
- **What the audit caught:** three agents invented CLI verbs (`kaos journal append`,
  `kaos skill signal`, `kaos experiment register`, `kaos checkpoint save`) and one invented a
  hooks.json schema. Checked against `kaos --help` and the plugin docs; corrected above. Two
  lessons went into KAOS memory (`agents-invent-cli`): seed the CLI reference into agent VFS
  before strategy runs, and the missing `kaos journal append` is a real gap M1 needs.
- One number was measured rather than taken from the agents: CLI cold start (710–830 ms
  here), which is why M1 specifies a lightweight hook entrypoint and ships the prompt-time
  hook off by default.
- Findings were written back with `kaos memory write` (keys `star-growth-pattern`,
  `kaos-next-moves-2026-09`, `agents-invent-cli`) and the evaluation logged with
  `kaos experiment log --family adoption`, so the +30/+60-day reviews can diff against it.
